# Feature Specification: 데이터 스냅샷과 출처 정보

**Feature Branch**: `claude/001-data-snapshot` (스펙 폴더는 `.specify/feature.json`으로 지정)

**Created**: 2026-10-14

**Status**: Approved (2026-10-14)

**Input**: 사용자 설명: "보고서를 검증하려면 너무 많은 것을 봐야 한다. 데이터 수집이 제대로 정리되어야 한다." — 로드맵 1단계 ([ROADMAP](../../ROADMAP.md))

## 배경

2026-10-14 세션에서 겪은 문제 대부분이 "숫자가 어디서, 어떤 기준으로, 언제 왔는지 모른다"에서 나왔다.

| 겪은 문제 | 원인 |
|---|---|
| '종가'가 출처마다 다름 (정규장 vs 수급 데이터) | 숫자에 가격 기준이 붙어 있지 않음 (KI-001) |
| 수급 금액을 정규장 종가로 잘못 '고침' | 수량과 가격이 같은 데이터에서 왔다는 정보가 없음 |
| 마이크론 사이클 판정이 갱신 시점에 따라 바뀔 수 있음 | 재무제표의 기준 기간이 표시되지 않음 (KI-003) |
| 기사 수치(하이닉스 10/12 -3.4%) 오인용 | 기사 수치를 수집 데이터와 대조할 수단이 없음 |
| 코스피 10/13 결측이 실행 시점마다 다름 | 실행 당시 데이터가 남지 않아 재현·검증 불가 (KI-002) |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 보고서 숫자의 출처 확인 (Priority: P1)

보고서를 검토하는 사람이 Section 4의 어떤 숫자를 보고, 그 값이 어느 출처의 어떤 기준(정규장 종가인지 수급 데이터 가격인지 등)·시점·상태(확정·잠정·추정·교정)인지 스냅샷 파일에서 바로 찾는다.

**Why this priority**: 이것이 없으면 다른 모든 검증(2단계 자동 대조 포함)이 불가능하다. 오늘 겪은 문제 5가지 중 4가지를 직접 막는다.

**Independent Test**: 보고서를 하나 생성하고, Section 4 표의 임의 값 하나를 골라 스냅샷에서 같은 값과 출처 정보를 찾을 수 있으면 통과.

**Acceptance Scenarios**:

1. **Given** 한국 종목이 포함된 보고서 생성, **When** 수급 표의 종가를 스냅샷에서 찾으면, **Then** `flow_feed_price` 기준 값과 같은 날의 `krx_regular_close` 값이 따로 있다.
2. **Given** 한국 종목 PER이 네이버 값으로 덮어써진 경우, **When** 스냅샷을 보면, **Then** 출처가 네이버이고 `original`에 Yahoo 값(또는 빈 값)이 있다.
3. **Given** 보고서 생성, **When** 보고서 상단을 보면, **Then** 짝이 되는 스냅샷 파일 이름이 적혀 있다.

---

### User Story 2 - 보완·교정 이력 추적 (Priority: P2)

검토자가 스크립트가 고친 값(예: Yahoo 빈 종가를 거래소 종가로 채움)을 원래 값과 사건 번호(KI)와 함께 확인한다.

**Why this priority**: 조용한 오류 금지(헌법 III)를 데이터 수준에서 보장한다. P1이 있어야 의미가 있다.

**Independent Test**: Yahoo 결측이 있는 날을 포함해 보고서를 만들고, 스냅샷에서 그 날짜 값이 `status: corrected`, `ki: KI-002`, `original`을 갖는지 확인.

**Acceptance Scenarios**:

1. **Given** Yahoo 종목·지수 이력에 빈 날이 있음, **When** 스냅샷을 보면, **Then** 그 값은 `corrected`이고 `ki`와 `original`이 있다.
2. **Given** ADR 통화 보정(KI-008), **When** 스냅샷을 보면, **Then** 보정 전 값과 보정 값이 함께 있다.

---

### User Story 3 - 나중에 재검증·재현 (Priority: P3)

며칠 뒤 다른 사람이나 다른 PC에서, 보고서 당시의 데이터·경고·실행 조건을 스냅샷만으로 확인한다.

**Why this priority**: 출처 데이터가 계속 바뀌므로(오늘도 코스피 10/13이 실행 시점마다 달랐다) 사후 검증에 필요하다. 2단계(자동 대조)의 입력이 된다.

**Independent Test**: 스냅샷의 메타 정보(시각, 인자, 라이브러리 버전)와 경고 목록이 보고서 Section 4 › 8번과 일치하는지 확인.

**Acceptance Scenarios**:

1. **Given** 보고서 생성, **When** 스냅샷 머리를 보면, **Then** 생성 시각(KST), 실행 인자, yfinance 버전, (가능하면) 스킬 저장소 커밋이 있다.
2. **Given** 데이터 품질 경고 발생, **When** 스냅샷을 보면, **Then** 같은 경고가 KI 번호와 함께 목록으로 있다.

---

### Edge Cases

- 스냅샷 저장 실패(권한·디스크): 보고서는 만들고, 보고서 상단과 데이터 품질 경고에 실패를 표시한다.
- 같은 날 보고서 재실행(`_v2`): 스냅샷도 같은 버전 이름을 쓰고 이전 파일을 덮어쓰지 않는다.
- 다음 금융 조회 실패: 교정 기록 없이 Yahoo 값과 실패 경고만 남긴다.
- 장중 실행: 시세·수급 값은 `provisional`로 기록한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 보고서마다 같은 이름의 스냅샷 `<보고서 파일명>_data.json`을 보고서 옆에 저장해야 한다. 기존 파일을 덮어쓰지 않는다.
- **FR-002**: 각 값은 `value`, `source`, `basis`, `as_of`, `status`를 가져야 한다. 필요하면 `note`, `ki`, `original`, `inputs`를 가진다.
- **FR-003**: `basis`는 정해진 어휘만 써야 한다. 최소 `krx_regular_close`, `flow_feed_price`, `yahoo_close`, `index_close`, `quote`, `statement`, `consensus`, `derived`를 구분한다. 어휘 밖의 값은 오류로 처리한다.
- **FR-004**: `status`는 `final`, `provisional`, `estimated`, `corrected`만 쓴다. `corrected` 값은 `original`과 `ki`를 함께 가져야 한다.
- **FR-005**: Section 4 표의 값은 모두 스냅샷에서 찾을 수 있어야 한다. 계산값은 입력값의 경로(`inputs`)를 기록한다.
- **FR-006**: 데이터 품질 경고를 KI 번호와 함께 스냅샷에도 목록으로 남긴다.
- **FR-007**: 스냅샷 머리에 생성 시각(KST), 실행 인자, 라이브러리 버전, 가능하면 스킬 저장소 커밋을 기록한다.
- **FR-008**: 스냅샷 저장에 실패해도 보고서는 만들고, 실패를 보고서와 경고에 표시한다.
- **FR-009**: 가격 이력은 종목·지수당 최근 260거래일의 종가·거래량만 담는다.
- **FR-010**: 새 분석은 과거 스냅샷을 읽지 않는다(헌법 VI). 검증 목적 비교는 사용자가 지정할 때만 허용한다.

### Key Entities

- **Snapshot**: 보고서 1개와 짝을 이루는 JSON 파일. `meta`, `values`, `series`, `warnings`로 구성.
- **Value record**: 점 표기 경로(예: `005930.KS.flows.2026-10-13.price`)를 키로 하는 값 1개와 출처 정보.
- **Series**: 종목·지수별 날짜→값 이력(종가·거래량)과 출처·기준.
- **Warning**: 데이터 품질 경고 문장과 KI 번호.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 전체 보고서 생성 시 `_data.json`이 함께 생기고 보고서 상단에 파일명이 표시된다.
- **SC-002**: Section 4 표 값(가격, 52주 범위, 수급, 기술적 지표 입력, 시장 비교, 핵심 지표, 사이클·밴드 입력, 컨센서스, 시나리오 입력)이 100% 스냅샷에 있다. 테스트로 확인한다.
- **SC-003**: 한국 종목 종가는 `krx_regular_close`와 `flow_feed_price`가 구분되어 있고, 보완·교정 값 100%에 `original`·`ki`가 있다.
- **SC-004**: 스냅샷 형식이 규칙 문서(`skills/financial-analyst/references/rules/data-snapshot.md`)에 정의되어 있다.
- **SC-005**: 기존·신규 테스트와 CI가 모두 통과하고, 같은 입력에서 판정 결과가 이전과 같다.
- **SC-006**: 스냅샷 크기가 종목 4개 기준 2MB 이하다.

## Assumptions

- 형식은 JSON 파일 하나로 한다(2026-10-14 결정). 가격 이력은 260일·종가·거래량만 담아 크기를 제한한다.
- 값 경로는 점 표기를 쓴다(2단계 자동 대조가 찾기 쉬움).
- 스냅샷을 Git에 넣을지는 분석 프로젝트(보고서 폴더)의 선택이며, 스킬 저장소는 관여하지 않는다.
- 저장소 커밋 정보는 얻을 수 있을 때만 기록한다(보고서가 저장소 밖에서 생성되므로).
- 범위 제외: 보고서 본문 자동 대조(002), 수집·계산 구조 분리(003), 공식 출처 전환(004).
