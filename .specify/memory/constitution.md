# value-chain-analysis-skills 헌법

투자 분석 스킬 3개(`skills/`)와 그 운영 지식을 함께 관리하는 저장소의 최상위 원칙입니다. 모든 스펙(`/speckit-specify`)·계획(`/speckit-plan`)·작업(`/speckit-tasks`)·구현은 이 원칙을 통과해야 합니다.

## 핵심 원칙

### I. 객관성 우선 (양보 불가)

스킬은 매수 근거를 찾는 도구가 아니라 판단을 검증하는 도구입니다. 판정은 스크립트의 규칙에서 나오고, 보고서 결론은 그 판정과 일치해야 합니다. 결론을 먼저 정하고 근거를 맞추는 기능·문구·기본값을 만들지 않습니다. 하락이나 낮은 배수 자체를 매수 신호로 쓰는 로직을 넣지 않습니다.

### II. 모든 숫자는 출처를 따라갈 수 있어야 한다

보고서와 위키의 숫자는 스크립트 산출값이나 인용 출처에서만 옵니다. 숫자에는 출처, 기준(예: 거래소 정규장 종가 vs 수급 데이터 가격), 시점, 상태(확정·잠정·추정·교정)를 붙일 수 있어야 합니다. 같은 '종가'라도 용도마다 맞는 기준이 다르면 섞지 않습니다(주가 등락은 정규장 종가, 수급 금액은 수급 데이터 가격).

### III. 조용한 오류 금지

데이터 출처가 틀리거나 비거나 구조가 바뀌면, 오류 없이 다른 값을 내는 대신 감지하고 경고합니다. 데이터 문제는 근거(`raw/`) → 사건 문서(`wiki/known-issues/`, KI 번호) → 코드 경고(`[KI-xxx]`) → 재현 테스트 순서로 처리합니다. 값을 보완·교정하면 원래 값과 사건 번호를 함께 남깁니다.

### IV. 규칙의 단일 원본

판정·데이터 규칙의 원본은 `skills/financial-analyst/references/rules/`입니다(스킬과 함께 배포). 기준값을 바꾸면 규칙 문서·코드·테스트를 같은 커밋에서 고치고, 이유를 `docs/decisions/`에 남깁니다. 같은 기준을 SKILL.md·보고서 문구에 다시 적을 때는 원본과 일치해야 합니다.

### V. 검증 가능한 변경

모든 변경은 CI(스크립트 문법, 테스트, 위키 근거 대조)를 통과해야 병합합니다. 판정·계산에 영향을 주는 변경은 같은 입력으로 수정 전후 결과를 비교하고, 판정이 바뀌면 이유를 PR에 적습니다. 검증하지 않은 것을 '완료'라고 쓰지 않습니다.

### VI. Clean-Slate

새 분석은 과거 보고서·스냅샷·기업별 결론을 입력으로 쓰지 않습니다. 위키에는 방법론과 데이터 품질 사실만 넣고, 기업별 판정·목표가·결론은 넣지 않습니다.

## 기술 제약

- 언어·실행: Python, `uv run --with-requirements`(가상환경 직접 관리 불필요). 주요 라이브러리: yfinance, pandas, requests, beautifulsoup4.
- 배포: 스킬은 `~/.claude/skills/`에 링크해서 쓰므로, 스킬 폴더 안에서 자기완결적이어야 합니다(실행에 필요한 규칙·스크립트는 스킬 폴더 안).
- 데이터 출처: Yahoo Finance, 네이버 금융, WiseReport, 다음 금융, Nasdaq.com은 비공식 경로입니다. 구조 변경에 대비해 검증 코드를 두고, 공식 출처(DART·SEC·KRX) 전환을 우선합니다.
- 플랫폼: Windows(PowerShell 5.1 이상)와 GitHub Actions(Ubuntu)에서 동작해야 합니다. Spec Kit 보조 스크립트는 PowerShell 버전을 씁니다.
- 출처 정기 점검(`check_data_sources.py`)처럼 국내 사이트 접속이 필요한 검사는 CI에 넣지 않고 로컬에서 실행합니다.

## 개발 흐름

- 새 기능·큰 변경: `/speckit-specify` → (`/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` → (`/speckit-analyze`) → `/speckit-implement`. 산출물은 `specs/NNN-이름/`에 둡니다. 범위가 바뀌면 spec부터 고칩니다.
- 작은 수정(버그 한 곳, 문서 오타, 경고 문구): 스펙 없이 진행할 수 있지만 원칙 III·V는 그대로 적용합니다.
- 브랜치는 `claude/...` 등 자유롭게 짓고 PR로 병합합니다. 현재 작업 중인 스펙 폴더는 `.specify/feature.json`(PC별, Git 제외)으로 지정합니다.
- 목표와 단계는 `ROADMAP.md`, 해야 할 작업은 GitHub Issues, 데이터 사실은 `wiki/`, 결정 이유는 `docs/decisions/`에 둡니다.

## 운영 규칙

이 헌법은 저장소의 다른 관행보다 우선합니다. 실행 방법과 명령은 `CLAUDE.md`와 `README.md`에 둡니다. 헌법을 고칠 때는 버전을 올리고(원칙 추가·삭제는 MAJOR, 원칙 보강은 MINOR, 문구 정리는 PATCH) `docs/decisions/`에 이유를 남깁니다. PR 검토 시 '헌법 점검'(위반 여부와 예외 사유)을 확인합니다.
