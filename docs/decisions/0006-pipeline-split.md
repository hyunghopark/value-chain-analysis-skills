# 0006. 원자료를 스냅샷에 저장하고, Section 4는 원자료에서만 만든다

- 상태: 채택
- 날짜: 2026-10-20
- 관련: [spec 003](../../specs/003-pipeline-split/spec.md), 규칙 원본 `skills/financial-analyst/references/rules/data-snapshot.md` §9

## 배경

001의 스냅샷은 Section 4에 찍힌 값의 기록일 뿐, Section 4를 만드는 입력이 아니었다. 수집·보완·계산·출력이 한 실행 안에 섞여 있었고, 표를 만드는 도중에도 외부에 접속하는 곳이 2곳(수급 표, 시장 비교 표), 현재 시각을 읽는 곳이 5곳 있었다. 그래서 같은 데이터로 보고서를 다시 만들 수 없었고, 판정 규칙을 바꿀 때 전후 비교가 실행 사이의 시세 변동에 섞였다(002 T037은 22초 간격 실행에서 2행이 달랐다).

## 결정

1. **외부 접속과 현재 시각 읽기는 `collect.py`에서만 한다.** 정제·계산·출력 코드는 네트워크 라이브러리를 import하지 않고 현재 시각을 읽지 않는다. 코드 검사 테스트(AST)와, 소켓·시각을 막고 실행하는 테스트로 지킨다.
2. **원자료를 통째로 저장한다.** 계산이 읽는 키·열만 골라 저장하면 코드가 새 키를 읽을 때 다시 빠진다(001의 '정해진 키 목록' 누락과 같은 실패). Yahoo `info` 전체, 시세 이력 전체 열, 재무제표·컨센서스 표 전체, 네이버·다음 응답 전체를 저장한다. 4개 종목 약 2MB로 측정됐다.
3. **표는 자료형·시간대 이름·날짜 정밀도·인덱스 이름까지 저장한다.** 인덱스를 글자로만 저장하면 실제 Yahoo 표 28개 중 9개가 다시 읽을 때 달라졌다. 시간대를 고정 오프셋으로 저장하면 서머타임 앞뒤가 섞이고, UTC로 바꾸면 한국 자정이 전날이 된다. 이 정보를 함께 저장하니 실제 표 38개가 모두 같았다.
4. **정제는 다시 실행한다.** 스냅샷에는 원자료를 두고, 덮어쓰기·KI 교정·출처 대조·경고를 Section 4를 만들 때마다 같은 규칙으로 다시 실행한다. 교정 전 원래 값이 원자료로 남고, 데이터 품질 규칙을 바꿀 때도 같은 입력으로 비교할 수 있다. 정제 결과만 저장하는 방식은 원래 값과 정제 코드의 변화를 확인할 수 없어 택하지 않았다.
5. **시각은 원자료마다 받은 시각을 쓴다.** 수급 표의 장 마감(15:40) 판단은 네이버 수급을 받은 시각, 실적 발표일과 해외 NTM 가중은 Yahoo `info`를 받은 시각, 국내 NTM 가중은 WiseReport 표를 받은 시각으로 정한다. 시각 하나로 통일하면 15:40 경계에 걸친 실행에서 지금과 판정이 달라진다. 표 머리의 생성 시각은 수집 완료 시각이며, 그래서 `meta.generated_at`의 뜻도 '저장 직전 시각'에서 '수집 완료 시각'으로 바뀌었다.
6. **수집 실패는 기록하고, 경고는 정제가 같은 자리에서 낸다.** 수집은 예외를 `status: error`와 메시지 글자로 남긴다. 정제는 그 메시지로 원래 `except` 자리에서 같은 경고를 낸다. 경고 순서가 코드 순서로 정해져 실행마다 같다. 스냅샷이 깨졌을 때의 오류(원자료 누락·형식 오류)는 `BaseException`에서 파생시켜, 기존 `except Exception` 블록이 이를 데이터 품질 경고로 바꾸지 못하게 했다(헌법 III).
7. **생성과 재현은 같은 길을 쓴다.** 보고서를 만들 때도 원자료를 JSON 글자로 바꿨다가 다시 읽은 뒤 Section 4를 만든다. 저장 형식에 문제가 있으면 생성 때 바로 드러난다.
8. **계산과 출력은 같은 표 함수에 남긴다.** 표 함수 15개를 '값 계산'과 '글자 만들기'로 나누면 약 1,500줄이 바뀌고 글자 단위 같음을 깨뜨릴 위험이 크다. 두 단계 모두 원자료만 읽는 순수 함수이고 계산 결과가 모두 `values`에 기록되므로, 재현·차단·'글자만 바뀐 변경' 구분은 모듈을 나누지 않아도 확인된다. 표 형식을 크게 바꿀 일이 생기거나, 계산 결과를 보고서 밖(예: 다른 도구)에서 직접 써야 할 때 다시 판단한다.
9. **형식 2 스냅샷 용량 기준은 10MB 이하로 둔다.** 001의 '4개 종목 2MB 이하'는 값 기록만 있을 때의 기준이다. 원자료를 넣으면 약 2.4MB(들여쓰기 2칸)가 되므로, spec 003 SC-007의 10MB로 바꾼다. 형식 1의 기준은 그대로다.
10. **CI 테스트는 pandas·numpy 버전을 고정한다.** 재현 테스트는 값을 정확히 비교하므로, 버전이 올라가면 무관한 PR이 실패할 수 있다. `tests/requirements-pinned.txt`에 시험 스냅샷을 만든 버전을 고정하고, 고정 버전과 시험 스냅샷의 기록 버전이 같은지 테스트로 확인한다. 버전을 올리려면 시험 스냅샷도 다시 만든다. 버전이 다를 때 테스트를 건너뛰는 방식은 조용한 실패라 택하지 않았다.

11. **계산값 비교는 부동소수점 오차를 허용한다(2026-10-20 추가).** PR #9 병합 후 x86_64 CI에서, arm64에서 만든 시험 스냅샷을 재현하니 기술 지표 7개가 마지막 자리(상대 약 5e-15)에서 달랐다. 같은 pandas·numpy라도 CPU 구조에 따라 이동 계산의 마지막 비트가 다르다(Docker로 x86_64·arm64 Linux에서 확인). 보고서를 만든 PC와 다시 만드는 PC가 다를 수 있으므로, 숫자는 상대 1e-9·절대 1e-12 안이면 같은 값으로 보고 그 경로는 `within_tolerance`로 따로 보여 준다. Section 4 글자는 계속 정확히 비교한다. 처음의 '정확히 같아야 한다'는 결정(R8)은 같은 플랫폼을 가정한 것이었다.

## 결과

- 장점: 보고서의 Section 4를 언제든 네트워크 없이 같게 다시 만들 수 있다. 판정 규칙 변경 PR은 같은 스냅샷으로 정확한 차이를 보여 준다. 분리 전 코드에 같은 원자료를 재생하니 Section 4 305줄이 모두 같았다.
- 단점: 스냅샷이 약 1.2MB에서 2.4MB로 커진다. pandas·numpy를 올릴 때 시험 스냅샷을 다시 만들어야 한다. 원자료를 쓰는 새 계산을 넣을 때는 `collect.py`에 수집 항목을 먼저 추가해야 한다(없으면 `missing_input`으로 바로 드러난다).
- 이전 형식(001·002) 스냅샷은 원자료가 없어 다시 만들 수 없다. 숫자 점검(002)은 두 형식 모두 쓸 수 있다.
